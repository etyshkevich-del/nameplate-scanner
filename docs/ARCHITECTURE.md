# Архитектура приложения

## Навигация

`LauncherActivity` открывает один из двух независимых пользовательских потоков.
Сценарий шильдика остаётся в `MainActivity`. RAG разделён на список диалогов,
экран файлов и экран сообщений, поэтому клавиатура и обработка документов не
конкурируют за место в одном длинном интерфейсе.

## Фото и Excel

`MainActivity` уменьшает изображение до допустимого для модели размера, учитывает
EXIF-ориентацию и передаёт PNG вместе с жёстко заданным JSON-контрактом в
LiteRT-LM. Ответ парсится только между первой `{` и последней `}`. Пользователь
проверяет значения до экспорта.

`WorkbookWriter` рассматривает XLSX как ZIP-контейнер. Он меняет только
`xl/worksheets/sheet1.xml`, экранирует пользовательские значения как XML и
перепаковывает остальные элементы без содержательных изменений.

## Документы и чаты

`RagStore` хранит данные внутри `filesDir/rag_v2`:

```text
rag_v2/
├── chats/<chat-id>.json
└── documents/
    ├── <sha256>.json
    └── <sha256>.txt
```

Идентификатор документа — SHA-256 исходного файла. Поэтому один текстовый слепок
может быть связан с несколькими чатами без повторного извлечения и хранения.
Сами чаты содержат список идентификаторов документов и историю сообщений.

## Выполнение модели

Один `Engine` LiteRT-LM создаётся внутри активного экрана. Сначала приложение
пытается использовать GPU, затем переключается на CPU. Перед отдельными задачами
создаётся новая `Conversation`, чтобы контекст распознавания и RAG не смешивался.

Модель поставляется как Android asset без сжатия и при первом запуске копируется
в приватный файл, доступный LiteRT-LM. Это удваивает постоянный объём модели на
устройстве, но позволяет runtime работать с обычным файловым путём.

## Системные панели и клавиатура

`RagChatActivity` работает edge-to-edge и самостоятельно применяет `WindowInsets`.
Нижний отступ равен максимальному inset клавиатуры или навигационной панели, поэтому
поле ввода остаётся над IME даже на устройствах, где `adjustResize` игнорируется.

## Потоки

Извлечение документов, индексирование, копирование модели и генерация выполняются
в одном фоновом executor каждого экрана. Изменения Android View возвращаются в
главный поток через `runOnUiThread`.
